## 1. Core Architecture & Mathematical Foundations

### Engineering problem

A training step maps tokens → logits → scalar loss → per-parameter gradients → one optimizer update. Session 10 requires proving that:

1. Autograd matches a hand nudge.
2. Micro-batch averaging can be silently wrong (~15.4%).
3. Grad norm can move before loss.
4. MFU can be poor while loss still falls.
5. Format choice (bf16 vs fp8 vs MXFP4) is visible in bit-level and block-scale error on `0.1`.

### Five-line loop

```python
logits = model(batch)          # forward
loss   = loss_fn(logits, y)    # one scalar
loss.backward()                # fill .grad (accumulate)
optimizer.step()               # update weights
optimizer.zero_grad()          # wipe (mandatory)
```

### MiniGPT tensors

| Tensor | Shape | Meaning |
| :--- | :--- | :--- |
| `idx` | `[B, T]` | batch, sequence length |
| hidden | `[B, T, D]` | `D` = `n_embd` |
| logits | `[B, T, V]` | `V` = vocab size |
| CE targets | `[B*(T-1)]` | next-token shift |

Default smoke config: `B=2`, `T=128`, `D=128`, `V=256`, `N ≈ 4.79e5` parameters (`src/llm/mini_gpt.py`).

### Hand gradient (Task 2)

For `h = w1 * x`, `y = w2 * h`, `L = (y - t)^2` with `x=2`, `w1=3`, `w2=4`, `t=20`:

```text
dL/dw1 = 64
```

Central difference in float64 must agree within `1e-4` ([`reports/assgn010_gradient_check.txt`](reports/assgn010_gradient_check.txt)).

### Accumulation bug (Task 3)

Token-weighted (correct) vs average-of-averages (buggy) on micro-batches with 4, 4, and 2 valid tokens:

```text
L_correct = 26/10 = 2.6000
L_buggy   = 9/3   = 3.0000
error     ≈ 15.38%
```

### MFU (Task 5)

```text
MFU = 6 * N * (tokens/s) / (peak TFLOP/s)
```

Assignment target **40%**; industry healthy band **35–50%**.

## 2. Hardware Constraints & Memory Footprint

### Adam / AdamW training state

Per trainable parameter (mixed precision):

| Component | Bytes |
| :--- | ---: |
| Weight (bf16) | 2 |
| Gradient (bf16) | 2 |
| Master weight (fp32) | 4 |
| Adam 1st / 2nd moment (fp32) | 8 |
| **Total** | **16** |

```text
Training state ≈ 16 * N bytes
```
(activations and KV cache extra).

Bottleneck on CPU: kernel launch / small-batch overhead, not H100 tensor cores. Values above are from the Colab CPU run in [`reports/assgn010_mfu_report.md`](reports/assgn010_mfu_report.md) (timing varies by machine). On a real GPU, recompute MFU with the device peak listed in that report.

### Long context

Staged curriculum (4K → … → 1M) must keep **global batch token count fixed per phase**. Longer `T` raises activation memory and accumulation steps → typically lower MFU unless checkpointing is retuned.

### Hand bits — target `0.1` (assignment)

| Format | Bits (sign exp mant) | Stored | Truncation |
| :--- | :--- | ---: | ---: |
| FP32 | `0 01111011 10011001100110011001101` | ≈ 0.10000000149 | ~0% |
| BF16 | `0 01111011 1001100` | 0.099609375 | **−0.39%** |
| FP8 E4M3 | `0 0011 101` | 0.1015625 | **+1.56%** |

`1.0` is exact in all three. Recommendation: **train in BF16** (FP32-class exponent range, no loss scaling). Details: [`reports/assgn010_precision_bits.md`](reports/assgn010_precision_bits.md).

### Full FP / block-scale table

Source: [`reports/assgn010_fp_format_table.md`](reports/assgn010_fp_format_table.md). Tensor: index 0 = `0.1`, index 1 = `5.0` outlier.

| Format | Layout | Read-back | Abs err % | Case |
| :--- | :--- | ---: | ---: | :--- |
| fp32 | 1+8+23 | 0.1 | 0.00 | Normal |
| fp16 | 1+5+10 | 0.099975586 | 0.02 | Normal |
| bf16 | 1+8+7 | 0.099609375 | 0.39 | Normal |
| fp8 E4M3 | 1+4+3 | 0.1015625 | 1.56 | Normal |
| fp8 E5M2 | 1+5+2 | 0.09375 | 6.25 | Normal |
| fp4 E2M1 | 1+2+1 | 0 | 100 | Underflow to zero |
| Custom | 1+6+9 | 0.099975586 | 0.02 | Normal |
| int8 | shared max/127 | 0.11811024 | 18.11 | Clamped/Scaled |
| MXFP4 | 32-el E2M1+E8M0 | 0 | 100 | Underflow to zero |
| NVFP4 | 16-el E2M1+E4M3 | 0 | 100 | Underflow to zero |
| MXFP4 + MBS | 128-el MBS + 32-el | 0.096191406 | 3.81 | **Rescued!** |
| MXFP4 + MBS + OAS | MBS + 16-el OAS | 0.096191406 | 3.81 | **Rescued!** |

**FP behaviour (this table).** Index 0 is `0.1` sitting next to a `5.0` outlier. Wider formats (fp32, fp16, bf16, E4M3, Custom) still represent `0.1` with growing truncation as mantissa bits shrink. Tiny per-value formats (fp4 E2M1) and **shared-scale** int8 / MXFP4 / NVFP4 let the outlier set the scale, so `0.1` **underflows to 0**. That is the silent precision bug analog of Session 10: loss can look fine while small values vanish.

**MXFP4.** Microscaling: E2M1 elements plus one E8M0 power-of-two scale per 32-element block. Advantage: ~4.5 bits/value and high throughput on modern GPUs; disadvantage: one large value poisons the whole block.

**NVFP4.** Same idea, 16-element blocks and an E4M3 fractional scale. Advantage: finer block scale than E8M0; still outlier-sensitive in this demo.

**MBS (Macro Block Scaling).** One high-precision (8-mantissa) scale over a larger 128-element macro-block isolates the outlier, then standard MXFP4 runs on 32-element blocks. Advantage: restores `0.1` (read-back ~0.096, **Rescued!**) so small activations survive.

**OAS (Overflow-Aware Scaling).** After MBS, 16-element micro-blocks may double local scale when the max sits in a headroom band `[3.0, 3.5]`. Advantage: uses more of the E2M1 range without overflowing; in this tensor it matches MBS (same rescue).

Focused MBS/OAS table: [`reports/assgn010_mbs_oas_table.md`](reports/assgn010_mbs_oas_table.md).
